- Decisions (with why):

  - **Did not rename `isInBand`'s parameters or add a `fish`/`box`-specific variant.** It's a generic symmetric range check with two legitimate call orderings; keeping it generic avoids two near-duplicate functions for no behavioral difference.

- Decisions (with why):
  - **Prestige/rating math was deliberately left as a no-op stub.** `CustomerFlow`'s "rating" stage still fires a `"left"` event on schedule, but `CustomerService` doesn't touch `restaurant.prestigePoints` when it fires — PRD's Yelp prestige formula is still Thread #6, unset, and TASKS.md already assigns "Prestige + traffic" to M12. Writing even a rough placeholder formula here would be inventing M12's answer inside M10's scope.
  - **Customers draw from the same `cookedPortions` pool the boat serve verb drains, not a separate restaurant stock.** PRD never describes two kitchens — "the supply chain IS the game" reads as one shared output competing across whatever's demanding it (a customer, or the player manually serving on the boat). Inventing a parallel stock pool would be a bigger unilateral mechanic decision than this session should make solo.
  - **`restaurant.staff` replaces `staffHeadcount` outright, not alongside it.** Deterministic per-staff performance needs each member's own `rarity`/`hiredAt` — keeping a redundant bare counter next to the real roster would be exactly the "divergent constant" dual-source-of-truth this codebase's own comments elsewhere warn against (see `EconomyConfig.lua`'s header on not duplicating `MAX_COOKING_LEVEL`).
  - **Tenure is wall-clock time since hired, not played-time.** PRD's "the longer you keep them" doesn't specify which; wall-clock reuses the exact elapsed-time-since-a-timestamp pattern every other clock in this repo already uses (freshness, spoilage, offline bank) instead of inventing a second time-tracking mechanism just for staff.
  - **Wages deduct live, every tick, clamped at 0 — not just reconciled via the offline bank.** PRD §5 lists wages as a continuous sink ("low early, a real line item at brick-and-mortar tier"), and `OfflineBankCalculator` only covers the logged-out window; without a live deduction, an online player with staff would never actually pay them.
  - **Auto-cook throughput scales with headcount (one fish per staff member per tick), not a flat one-per-tick regardless of hires.** PRD §4 names kitchen throughput as staff-driven ("hire cooks... who perform cooking and serving automatically") and the primary bottleneck — a flat rate would make hiring a second cook pointless, contradicting the design's own headcount economy.
