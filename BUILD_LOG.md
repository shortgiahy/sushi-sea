## 2026-07-28 — M3 fishing feel slice, gray-box (dev-gameplay)
- Done (branch `claude/sushi-m3-fishing-feel`): full cast→hook→reel loop, gray-box `Part`s only. `FishingController.lua` (client): raycast-driven cast targeting with a fallback for a world with no water geometry yet, a code-built HUD (prompt label + tension bar with a static target-zone highlight + progress bar), a gray-box bobber `Part` with cast-flight and bite-flash tweens, hold-to-raise/release-to-fall tension input (mouse, touch, and Space all map to one action), and a `RunService.Heartbeat` loop that renders tension locally every frame while sending `Player_ReelInput` at a throttled rate. `EconomyService.server.lua` (server): validates and rate-limits `Player_CastLine`/`Player_ReelInput`, runs the authoritative fight simulation, and resolves catch identity (species + quality) via a weighted roll — never a price. `FishingCatch.lua` (new, `ServerStorage/Modules/`): the pure, Roblox-global-free validation/fight-sim/catch-roll logic, unit tested in `tests/FishingCatch.spec.luau` (14 assertion blocks: location/tension validation, cooldown + pending-cast + reel-input-throttle gating, hook-window/fight-budget timeouts, in-band progress accumulation to a catch, out-of-band decay without failure, snap-on-overtension, weighted species selection at roll boundaries, authored quality-band boundaries, degenerate empty/zero-weight species tables). `FishingConfig.lua` (new, `shared/Config/`) holds every tuning constant with a doc-comment block explaining the reasoning for each starting value. `FishSpecies.lua` filled with 5 placeholder species (3 rarity tiers, catch weights, no prices). 4 new RemoteEvents (`Player_CastLine`, `Player_ReelInput`, `Fishing_BiteWindow`, `Fishing_FightResult`) declared directly in `default.project.json` as Rojo-managed `RemoteEvent` instances rather than created by a bootstrap script, matching the file-first/repo-is-source-of-truth stance (PRD §9). Added `src/client/Bootstrap.client.lua` (mirrors the server Bootstrap pattern) so `FishingController.init()` actually runs — otherwise the module would be authored but never wired, failing PRD §11's DoD.
- Verified: `lune run` on all 4 spec files (`FishingCatch`, `PlayerDataSchema`, `DataStoreRetry`, `placeholder`) — all pass. `rojo build -o *.rbxlx` succeeds with the new RemoteEvent tree. `selene src` — 0 errors/0 warnings across the whole tree (found and fixed 10 warnings in `FishingController.lua`: an unused local and several `UDim2.new` calls simplified to `fromOffset`/`fromScale`). `stylua --check` — every file this session touched is clean; **could not get a clean `stylua --check src` run on the full tree**, because every file from before this session (`WeatherClient.lua`, `PlayerDataSchema.lua`, `Bootstrap.server.lua`, etc.) is checked out with CRLF line endings on this Windows sandbox while `stylua.toml` requires Unix endings — confirmed this is a local-checkout artifact (git autocrlf on Windows), not a real defect, since CI runs on `ubuntu-latest` where checkout doesn't rewrite line endings; flagging so it isn't mistaken for a regression if someone re-runs stylua locally on Windows. **Not verified — no Roblox Studio available in this sandbox:** the actual feel (this is explicitly the point of M3 and cannot be certified here), the raycast-based cast-targeting against real geometry, GUI layout/readability on an actual screen, and mobile touch input.
- Decisions (with why):
  - **RemoteEvent payload shape: always a single table, e.g. `{ location = ... }` / `{ tension = ... }`.** PRD §7.2 writes every event's fields inside `{...}` uniformly regardless of arity (`Player_CastLine — {location}` has exactly one field but is still shown in braces), read as "the payload shape," not "wrap only if >1 field." Table payloads are also strictly more extensible (a future field doesn't break the call signature) at negligible cost.
  - **`FishingCatch.lua` takes config as explicit parameters instead of `require`ing `FishingConfig`/`FishSpecies` directly.** Those live in `ReplicatedStorage`, reachable only via `game:GetService(...)`, which doesn't exist under the headless Lune test runner. `DataStoreRetry.lua` solved an analogous problem with a runtime-detection branch (`if task ~= nil then task else require("@lune/task")`); dependency injection was simpler here and keeps the pure module honestly zero-Roblox-globals rather than conditionally so.
  - **`FishTable.lua` was NOT touched — species identity data went in `FishSpecies.lua` instead.** `FishTable.lua`'s documented role (and PRD §5/§7.1's) is specifically the authored `species -> base_price` economy lookup, explicitly scoped to M5 (~10 species, all 4 plate-value multipliers). `FishSpecies.lua` is already documented as "no prices here, see FishTable" — exactly the shape M3 needs (identity + rarity, no economy). Populating `FishTable.lua` now with a partial M3-scoped species list risked colliding with or pre-empting M5's authored table.
  - **Caught fish are NOT written to `PlayerDataService` inventory in this stub.** `EconomyService.server.lua` and `PlayerDataService.server.lua` are separate Scripts that each currently self-wire independently; `Bootstrap.server.lua` is still an empty stub with no service-registry/injection pattern for one Service to reach another's owned state. Inventing that cross-service wiring as a side effect of the fishing stub would be an undocumented architecture decision. It belongs with M4, which needs the identical access to feed `ConversionModule.cook(fish)` anyway — the natural point to decide it once, not twice.
  - **New server→client events (`Fishing_BiteWindow`, `Fishing_FightResult`) added beyond PRD §7.2's three listed examples.** The naming convention (`{System}_{Event}`) is the actual rule; none of the three listed examples (`Weather_StormBroadcast`, `Economy_PlateResolved`, `Spoilage_InventoryUpdate`) cover fishing, and the loop needs server→client bite/result signaling to exist at all. No third client→server event was added for "hook" — the hook reaction is captured implicitly by how quickly the client's first `Player_ReelInput` arrives after `Fishing_BiteWindow`, staying within the two remotes named in the task's exact contract.
  - **No miss/no-bite chance in this slice — every cast eventually gets a bite.** Adding a spawn/miss-chance table now would start overlapping M13/M14's weather-driven spawn-table scope; out of bounds for a slice that's explicitly about the three verbs (cast/hook/reel), not the spawn system.
  - Tuning starting points and full reasoning for every constant live as a doc comment in `FishingConfig.lua` (cooldown/bite-wait pacing, a wide/forgiving tension band for mobile-compat, progress gain/decay rates sized to a ~12s fight budget, decay-not-failure on out-of-band tension matching Pillar 1's opportunity-cost framing). Not repeated here — treat that file as the single source for "why these numbers."

The real open item is the feel gate itself (ROADMAP Phase 2 🔶): this build is a reasoned starting point for Giahy (or a recruited playtester) to iterate on in Studio, not a claim that the rod already feels good. Also open, deferred to M4 by the reasoning above: the PlayerDataService cross-service access pattern for writing caught fish to inventory.
